--------------------------------------------------------------------------------
WHAT THIS PROJECT IS
--------------------------------------------------------------------------------
RealChain v2 is a blockchain-based fractional real estate investment platform.
A property owner tokenizes their property into 100 ERC-20 tokens. Investors
buy those tokens using USDC (a stablecoin = always $1). The owner deposits
monthly rent in USDC. Investors claim their proportional share of rent based
on how many tokens they held at deposit time (not at claim time — this is the
core security fix). Investors can also sell their tokens to other investors on
a built-in marketplace.

Everything runs on Ethereum smart contracts. No bank. No middleman. No trust.

There are TWO versions of the dividend contract:
  V1 (RentalDistribution.sol)   — loop-based, O(n) gas, simpler
  V2 (RentalDistributionV2.sol) — accumulator-based, O(1) gas, more complex

The factory deploys either V1 or V2 depending on a flag. Default is V1.

--------------------------------------------------------------------------------
THE CORE SECURITY PROBLEM THIS PROJECT SOLVES
--------------------------------------------------------------------------------
Naive dividend contracts use balanceOf(user) at CLAIM time to calculate share.
This is exploitable:

  1. Owner deposits 1000 USDC rent at block T
  2. Attacker Carol buys 30 tokens at block T+1 (AFTER rent deposit)
  3. Carol calls claimAll() — gets 300 USDC she never earned
  4. Alice sold tokens before claiming — gets 0 USDC even though she held
     tokens during the rental period

FIX: Record block.timestamp - 1 as snapshotTime when rent is deposited.
Use ERC20Votes.getPastVotes(user, snapshotTime) instead of balanceOf().
getPastVotes() returns what the user held ONE SECOND BEFORE the deposit.
Carol held 0 at that time → gets 0. Alice held 30 → gets 300.

This is proven in test/SnapshotAttack.test.js.

CONTRACTS/ — FILE BY FILE
--------------------------------------------------------------------------------

MockUSDC.sol
  What: A fake USDC token for testing. ERC-20 with 6 decimal places.
  Why: Real USDC doesn't exist on local Hardhat. We need a stablecoin.
  Key detail: 6 decimals means 1 USDC = 1_000_000 (one million units).
              So $500 USDC = 500_000_000 in raw contract numbers.
  Who uses it: Everyone. All rent deposits, token purchases, and dividend
               claims use MockUSDC as the settlement currency.
  Owner can mint arbitrary amounts (used in deploy.js and tests).

PropertyToken.sol
  What: The fractional ownership token for one property. ERC-20Votes.
  Why ERC20Votes (not plain ERC-20): ERC20Votes automatically records a
    checkpoint (timestamp, balance) every time tokens are transferred.
    This enables getPastVotes(user, timestamp) — looking up historical balance.
    Plain ERC-20 only knows current balance, not past balance.
  Why ERC20Votes (not ERC20Snapshot): ERC20Snapshot needs a manual
    snapshot() call before every deposit. If you forget, no historical data.
    ERC20Votes checkpoints happen automatically on every transfer.
  Supply: Exactly 100 tokens per property (100 * 10^18 in wei).
  Clock mode: Uses block.timestamp (not block.number). Required because
    RentalDistribution uses timestamp math, not block numbers.
  Auto-delegation: ERC20Votes requires users to call delegate(self) before
    their balance shows up in getPastVotes(). Most users won't know to do this.
    We override _update() to auto-delegate on first token receipt:
      if (delegates(to) == address(0)) { _delegate(to, to); }
    Without this, new investors would silently get 0 dividends forever.
  Owner: PropertyFactory is the owner. Can only mint during deployment.

PropertyFactory.sol
  What: Registry and deployer. Creates one property = 3 contracts atomically.
  Why: Instead of deploying Token, RentalDistribution, Marketplace separately
    (and manually linking them), the factory does it in one transaction.
  What it deploys per property:
    - PropertyToken (100 PROP tokens, minted to the property owner)
    - RentalDistribution V1 OR V2 (based on useV2 flag)
    - RentalDistributionV2Deployer (if V2 — needed for contract size limit)
    - Marketplace
  Storage: properties[] array. Each entry has:
    { owner, propertyToken, rentalDistribution, marketplace, name, location,
      totalValue, useV2 }
  Key functions:
    createProperty(name, location, totalValue, useV2) — deploys 3 contracts
    getPropertiesCount() — how many properties exist
    properties(index) — get addresses for property at index
  Gas cost: ~4 million gas per property (~$162 at 20 gwei, ETH=$2000).
    This is expensive because it deploys 3 contracts in one tx.
    Future fix: ERC-1155 multi-token standard (one contract for all properties).

RentalDistribution.sol  (V1 — the default)
  What: Handles monthly rent deposit and investor dividend claiming.
  How dividends work:
    1. Owner calls depositRental(amount) — transfers USDC from owner to contract
    2. Contract records: { totalAmount, snapshotTime = block.timestamp - 1 }
       (snapshotTime is one second BEFORE this block to prevent same-block attacks)
    3. Investor calls claimAll() — loops through all unclaimed epochs
    4. For each epoch: share = (getPastVotes(user, epoch.snapshotTime) / totalSupplyAt) * epoch.totalAmount
    5. USDC transferred to investor
  Security:
    - ReentrancyGuard (nonReentrant modifier on claim functions)
    - Checks-Effects-Interactions: claimed[epoch][user] = true BEFORE USDC transfer
    - getPastVotes() prevents post-deposit purchasers from claiming
  Gas complexity: O(n) — linear with number of unclaimed epochs
    1 epoch  → 85,525 gas
    12 epochs → 433,324 gas
    48 epochs → 1,571,591 gas
  Formula: Gas(n) = 85,503 + (n-1) * 42,858
  Key functions:
    depositRental(amount) — onlyOwner, creates new epoch
    claimAll() — claims all unclaimed epochs for caller
    claimEpoch(index) — claims one specific epoch
    pendingDividends(user) — view: how much user can claim right now
    epochCount() — how many epochs exist
    epochs(index) — get epoch data

BrokenRentalDistribution.sol
  What: Intentionally VULNERABLE version of RentalDistribution.
  Why it exists: Research baseline. Proves the attack works.
  The bug: Uses balanceOf(user) at claim time instead of getPastVotes().
    function pendingDividends(address user) {
      uint256 userBalance = propertyToken.balanceOf(user); // WRONG — live balance
      ...
    }
  Who deploys it: Only the test suite (SnapshotAttack.test.js).
  NEVER deployed in production scripts.

RentalDistributionV2.sol  (V2 — optional, O(1) gas)
  What: Alternative dividend distribution using accumulator pattern.
  How it works (different from V1):
    - Global variable: accRewardPerToken — tracks cumulative USDC per token
    - On each deposit: accRewardPerToken += (depositAmount * PRECISION) / totalSupply
    - Each user has rewardDebt — records accRewardPerToken when they last claimed
    - claimAll(): userReward = (balance * accRewardPerToken / PRECISION) - rewardDebt
    - No loop. Constant time regardless of how many deposits happened.
  Transfer-time fairness: Uses IDDistributionHook interface.
    Before token transfer: seller's pending rewards are settled (locked in)
    After token transfer: buyer's rewardDebt is updated to current accRewardPerToken
    This ensures seller gets paid for epochs they held through, buyer doesn't steal.
  Gas complexity: O(1) — constant regardless of epoch count
    Always ~137,616 gas for claimAll(), whether 1 or 48 epochs
  Tradeoff: Each deposit costs more gas than V1 (178,514 vs 147,968)
  When to use V2: If N_claims × (V1_gas - V2_gas) > N_deposits × 30,546 + N_transfers × 47,607
    Rule of thumb: V2 wins if users claim more than ~3 unclaimed epochs on average.

RentalDistributionV2Deployer.sol
  What: A separate contract that deploys RentalDistributionV2.
  Why it exists: RentalDistributionV2.sol is large. If PropertyFactory
    tried to deploy it directly, the factory contract itself would exceed
    Ethereum's 24KB contract size limit (EIP-170). So we use a separate
    deployer contract to stay under the limit.
  Who uses it: PropertyFactory calls this internally when useV2=true.
  You never interact with this directly.

IDistributionHook.sol
  What: Solidity interface defining two callback functions:
    onBeforeTokenTransfer(from, to, amount)
    onAfterTokenTransfer(from, to, amount)
  Who implements it: RentalDistributionV2.sol
  Who calls it: PropertyToken._update() (the transfer hook)
  Why: Allows RentalDistributionV2 to settle pending rewards at transfer time
    so the ERC20Votes checkpoint and the dividend accounting stay in sync.

Marketplace.sol
  What: Handles buying/selling property tokens using USDC.
  Two markets:
    PRIMARY: Owner sells tokens directly to first investors
      - Owner lists via implicit availability (they hold unsold tokens)
      - Investor calls buyFromOwner(propertyAddress, amount)
      - USDC flows: investor → owner (minus 0% fee currently)
    SECONDARY: Token holders sell to other investors peer-to-peer
      - Holder calls createListing(amount, pricePerToken)
      - Buyer calls buyFromListing(listingId)
      - USDC flows: buyer → seller
  Security:
    - ReentrancyGuard on all buy functions
    - CEI pattern: state updated BEFORE USDC transfer
    - approve() required before any purchase (ERC-20 standard)
  Two-step purchase flow (required by ERC-20):
    Step 1: investor calls usdc.approve(marketplace, totalCost)
    Step 2: investor calls marketplace.buyFromOwner(amount)
  Key functions:
    buyFromOwner(propertyToken, amount) — primary market purchase
    createListing(amount, pricePerToken) — create secondary market listing
    buyFromListing(listingId) — buy from secondary market
    cancelListing(listingId) — cancel your own listing
    listings(id) — get listing data

TEST/ — FILE BY FILE (31 TESTS TOTAL, ALL PASSING)
--------------------------------------------------------------------------------

RealEstatePlatform.test.js  (17 tests)
  Coverage: End-to-end happy path for the entire platform.
  Tests: Factory deployment, token minting, USDC balance checks,
    buying tokens from owner, creating/buying secondary listings,
    depositing rent, claiming dividends, snapshot correctness,
    V2 contract invariants.
  This is the main functional test suite. If this passes, the platform works.

SnapshotAttack.test.js  (5 tests)
  Coverage: Formal proof of the security vulnerability and its fix.
  Setup: Deploys BOTH BrokenRD and FixedRD against the SAME PropertyToken.
  Tests:
    Phase 1: Initial state (Alice=30, Bob=20, Owner=50, Carol=0)
    Phase 2: Owner deposits 1000 USDC (epoch created)
    Phase 3: Carol buys Alice's 30 tokens (AFTER deposit)
    Phase 4 [BROKEN]: Carol gets 300 USDC (stolen), Alice gets 0 (robbed)
    Phase 5 [FIXED]:  Carol gets 0 USDC (blocked), Alice gets 300 (correct)
  This is the core research contribution. The test output is Table I in paper.

GasBenchmark.test.js  (3 tests)
  Coverage: Gas cost of claimAll() across different epoch counts (V1 only).
  Tests:
    Test 1: claimAll() at epochs 1, 3, 6, 12, 24, 48 — measures gas each time
    Test 2: All core function gas costs (createProperty, buyFromOwner, etc.)
    Test 3: Minimum viable stake — when is it economically rational to claim?
  Output: Prints tables directly to terminal. Data used in paper Section V.
  Key finding: Gas(n) = 85,503 + (n-1) * 42,858 (linear, R² > 0.999)

DistributionV2.test.js  (3 tests)
  Coverage: V2 contract invariants and fairness.
  Tests:
    - Transfer-time fairness: seller's rewards settled before transfer
    - Buyer cannot claim rewards from before they bought tokens
    - accRewardPerToken math is correct after multiple deposits

FactoryDistributionMode.test.js  (2 tests)
  Coverage: Factory correctly deploys V1 or V2 based on useV2 flag.
  Tests:
    - useV2=false deploys V1 (loop-based claimAll works)
    - useV2=true deploys V2 (constant gas claimAll works)

V1VsV2Benchmark.test.js  (1 test)
  Coverage: Side-by-side gas comparison of V1 and V2.
  Output: Prints benchmark table to terminal. Data used in paper Table IV.
  Key finding: V2 is always 137,616 gas. V1 grows from 102,625 to 1,588,691.

frontend/src/context/Web3Context.jsx
  The brain of the frontend. Provides blockchain state to all components.
  Two provider architecture:
    READ-ONLY provider (JsonRpcProvider):
      - Connects directly to http://127.0.0.1:8545
      - No MetaMask needed
      - Used for: loading properties, reading balances, reading epoch history
      - Created once and cached (singleton pattern)
    SIGNER provider (BrowserProvider wrapping MetaMask):
      - Requires MetaMask to be installed and connected
      - Used for: buying tokens, depositing rent, claiming dividends
      - Only created when user clicks "Connect Wallet"
  State it tracks:
    account — connected MetaMask address (null if not connected)
    signer — ethers Signer object for writing transactions
    chainId — which network MetaMask is on
    usdcBalance — current USDC balance of connected account
    roleHint — "Owner" or "Investor" based on on-chain data
    nodeOnline — true/false whether Hardhat node is reachable
    error — any connection error message
  Key functions exposed to components:
    connect() — triggers MetaMask connection popup
    switchAccount() — triggers MetaMask account picker
    switchToExpectedNetwork() — auto-adds Hardhat Local to MetaMask
    getReadFactory() — read-only PropertyFactory contract instance
    getReadPropertyContracts(addresses) — read-only {token, rental, market}
    getFactory() — writable PropertyFactory (needs signer)
    getUsdc() — writable MockUSDC (needs signer)
    getPropertyContracts(addresses) — writable {token, rental, market}
    refreshUsdcBalance() — re-fetches USDC balance
    fmtUsdc(raw) — formats 6-decimal USDC to "$X.XX"
    fmtProp(raw) — formats 18-decimal PROP token to "X.XX"

frontend/src/pages/Home.jsx

frontend/src/pages/Property.jsx

  Data loading: Uses read-only provider for all display data.
  Buying tokens (requires wallet):

    2. Frontend calculates cost = amount * pricePerToken
    3. Calls usdc.approve(marketplace, cost) — MetaMask popup 1

frontend/src/pages/Portfolio.jsx
  Shows the connected user's holdings across all properties.
  What it shows:
    - Each property where user holds > 0 tokens

  Data loading:

frontend/src/pages/Dividends.jsx

HOW EVERYTHING CONNECTS (DATA FLOW)
--------------------------------------------------------------------------------

DEPLOYMENT FLOW:
  deploy.js
    → deploys MockUSDC (gets address)
    → deploys PropertyFactory (passes mockUSDC address)
    → calls factory.createProperty("Palm Heights", ..., useV2=false)
      → factory deploys PropertyToken (passes mockUSDC, owner address)
      → factory deploys RentalDistribution (passes token, mockUSDC)
      → factory deploys Marketplace (passes token, mockUSDC)
      → factory stores all 3 addresses in properties[]
    → writes all addresses to deployed-addresses.json

FRONTEND STARTUP FLOW:
  main.jsx renders App wrapped in Web3Provider
  Web3Context starts:
    → creates JsonRpcProvider (read-only, no MetaMask)
    → pings getBlockNumber() to check if node is online
    → sets nodeOnline = true/false
  Home.jsx mounts:
    → calls getReadFactory()
    → calls factory.getPropertiesCount()
    → calls factory.properties(0), factory.properties(1), ...
    → renders property cards

USER BUYS TOKEN FLOW:
  User clicks "Connect Wallet"
  → Web3Context.connect() → MetaMask popup
  → signer created, account set, chainId set
  User enters amount on Property.jsx
  → frontend calculates cost
  → calls usdc.approve(marketplaceAddress, cost) → MetaMask popup 1
  → calls marketplace.buyFromOwner(propertyTokenAddress, amount) → MetaMask popup 2
  → marketplace calls usdc.transferFrom(buyer, owner, cost)
  → marketplace calls token.transferFrom(owner, buyer, amount)
  → PropertyToken._update() fires → auto-delegates buyer → ERC20Votes checkpoint written
  → refreshUsdcBalance() called → UI updates

OWNER DEPOSITS RENT FLOW:
  Owner goes to Dividends page, enters 1000 USDC
  → calls usdc.approve(rentalAddress, 1000_000_000) → MetaMask popup 1
  → calls rental.depositRental(1000_000_000) → MetaMask popup 2
  → rental: records epoch { totalAmount=1000 USDC, snapshotTime=block.timestamp-1 }
  → UI refreshes, new epoch appears in table

INVESTOR CLAIMS FLOW:
  Investor clicks "Claim All" on Dividends page
  → calls rental.claimAll() → MetaMask popup
  → rental loops through all unclaimed epochs
  → for each: share = getPastVotes(user, epoch.snapshotTime) / totalSupplyAt * epochAmount
  → for each: claimed[epoch][user] = true (state update first — CEI)
  → for each: usdc.transfer(user, share) (external call last — CEI)
  → investor's USDC balance increases
  → refreshUsdcBalance() → UI updates

HOW TO RUN THE PROJECT (QUICK REFERENCE)
--------------------------------------------------------------------------------

  cd e:\Reel-Estate-BT-master\Reel-Estate-BT-master
  npm install
  cd frontend && npm install && cd ..

  npx hardhat compile

  http://localhost:3000

  Import a Hardhat test account (private key printed by hardhat node in Terminal 1)
